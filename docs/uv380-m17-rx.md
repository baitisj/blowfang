# M17 receive on the UV-380, no hardware mod

*2026-11-18. Milestone 2 of [the M17 scope](uv380-m17-scope.md): find a receive path for M17
(4800 baud 4FSK, RRC alpha 0.5, +-2400 Hz outer) on the unmodified MD-UV380. Upstream OpenRTX
receives M17 on this radio only after a solder mod (RF audio to the MCU's PC3 ADC). Transmit
already works through the C6000's physical layer mode (milestone 1, 0 bits wrong on air).*

## Two candidate paths, measured in one bench session

| | Path A: the chip's own demodulator | Path B: the FM tap |
| --- | --- | --- |
| What | C6000 physical layer test mode (0x10 = 0x02, 0x40 = 0x40, 0x41 = 0x41), AT1846S in its DMR set: the chip slices 4FSK and leaves each 288-bit window (36 bytes, 30 ms) at RX RAM 0x30, plus per-symbol soft values at 0x0A8 / 0x1C8 | C6000 in FM receive: 8 kHz 16-bit discriminator audio in RX RAM 0x030-0x22F / 0x230-0x42F, a half per 32 ms, after page 4 0x34's filters (RadioFoundry `modem-hrc6000.md` 8.1, MIT) |
| M17 fit | same symbol rate and dibit map as DMR; the chip's matched filter is alpha 0.2 (sim: about 30 dB signal to ISI against an alpha 0.5 sender); slicer thresholds are set for DMR's 1944 Hz, M17 sends 2400 | needs DC coupling (a high pass under about 20 Hz, sim in the scope) and a flat band to about 3 kHz |
| Risk | does the chip keep symbol timing and hand over every window with no symbol lost or doubled, without a DMR sync? Our 11-16 raw test (`c6dmrrx_raw`, IC-7100 pre-emphasised source) got windows every slot but misaligned with DMR bursts, which a continuous M17 stream doesn't care about | RadioFoundry saw "a fixed sub-audio high-pass, about 20 dB down below 300 Hz" on the tap; in the sim a 300 Hz corner closes the eye completely |
| MCU cost if it works | almost none: 36 bytes per 30 ms over SPI, sync search and Viterbi on hard (or soft) decisions | 512 bytes per 32 ms, x3 interpolation and OpenRTX's demodulator at 24 kHz |
| Module | `c6phyrx.c` (c6dmrrx with RX_RAW, soft values every 8th window) | `c6fmtap.c` (0x34 stepped every 5 s through 1c, 18, 3c, 9c) |

Both modules are receive only: no `tx_tone`, no key-up, registers and the AT1846S put back at the
end. A path B result also settles where the UV-380's ~300 Hz receive high pass comes from.

## Test signal (Pluto, 441.850, AG7EW MCW ident first and last)

`python3 -m modem.m17rx wav OUT.wav` makes it at 48 kHz, half scale (`pluto_bench.py send OUT.wav
--dev 4800` = M17's 2400 Hz outer; `--dev 3888` = DMR's 1944):

- 30 s multitone: 10, 20, 30, 50, 75, 100, 150, 200, 300, 500, 700 Hz, 1, 1.5, 2, 2.5, 3, 3.4,
  3.8 kHz at equal level, Schroeder phases, 0.2 s period, so any whole second gives the response
  on exact FFT bins;
- 30 s of spec M17 BERT (PRBS9, alpha 0.5, 750 frames). `--tones-s 0 --bert-s 10` gives BERT only.

## Bench jobs (jobs inbox, UV-380 receive only)

**R1 tap** (`m17rx-tap-*`): `uv380.cmd` listen 0, power 0, freq 441850; `uv380.rx tap` in the
background; wait for `tap start`; `pluto send job:m17rx.wav --dev 4800 --gain -50`; wait for
`end halves`.

**R2 phy** (`m17rx-phy-*`): the same with `uv380.rx phy`, then four Pluto sends of `bert10.wav`:
2400 Hz outer, 1944 Hz outer, and 2400 Hz at +-500 Hz carrier offset (how much the slicer
tolerates; `st` lines log the ADC's own DC offset, 0x4E / 0x4F).

Read them: `python3 -m modem.m17rx tap uv380.log --wav tap.wav` (per 0x34 setting: tone response
against 1 kHz, where it is within 3 dB, BERT frames and bit errors from the tap) and
`python3 -m modem.m17rx phy uv380.log` (window spacing, BERT syncs in the joined windows, the gaps
between them, 192 symbols = nothing lost, bit errors; the soft level histogram).

| Result | Then |
| --- | --- |
| A: syncs 192 symbols apart, BER low | M17 RX on the chip: an RX module (sync search, LSF, stream, Codec2 out the speaker), then the image's M17 mode on this path, then upstream |
| A: windows lose or double symbols | try 0x10 = 0x66 (slotted) and the 0x40 timing bits; the soft values may still carry the symbols |
| B: low corner under ~20 Hz with some 0x34 | software demodulator on the tap (OpenRTX's own, 8 kHz input, x3) |
| B: ~300 Hz high pass whatever 0x34 says | the tap is out for 4FSK (the sim); A or nothing without a mod |
