# M17 receive on the UV-380, no hardware mod

*2026-11-18. Milestone 2 of [the M17 scope](uv380-m17-scope.md): find a receive path for M17
(4800 baud 4FSK, RRC alpha 0.5, +-2400 Hz outer) on the unmodified MD-UV380. Upstream OpenRTX
receives M17 on this radio only after a solder mod (RF audio to the MCU's PC3 ADC). Transmit
already works through the C6000's physical layer mode (milestone 1, 0 bits wrong on air).*

## Two candidate paths, measured in one bench session

| | Path A: the chip's own demodulator | Path B: the FM tap |
| --- | --- | --- |
| What | C6000 physical layer test mode (0x10 = 0x02, 0x40 = 0x40, 0x41 = 0x41), AT1846S in its DMR set: the chip slices 4FSK and leaves each 288-bit window (36 bytes, 30 ms) at RX RAM 0x30, plus per-symbol soft values at 0x0A8 / 0x1C8 | C6000 in FM receive: 8 kHz 16-bit discriminator audio in RX RAM 0x030-0x22F / 0x230-0x42F, a half per 32 ms, after page 4 0x34's filters (RadioFoundry `modem-hrc6000.md` 8.1, MIT) |
| M17 fit | same symbol rate and dibit map as DMR; the chip's matched filter is alpha 0.2 (sim: about 30 dB signal to ISI against an alpha 0.5 sender); slicer thresholds are set for DMR's 1944 Hz, M17 sends 2400 | needs DC coupling (a high pass under about 20 Hz, sim in the scope) and a flat band to about 3 kHz |
| Risk | does the chip keep symbol timing and hand over every window with no symbol lost or doubled, without a DMR sync? Our 11-16 raw test (`c6dmrrx_raw`, IC-7100 pre-emphasised source) got windows every slot but misaligned with DMR bursts, which a continuous M17 stream doesn't care about | RadioFoundry saw "a fixed sub-audio high-pass, about 20 dB down below 300 Hz" on the tap; in the sim a 300 Hz corner closes the eye completely |
| MCU cost if it works | almost none: 36 bytes per 30 ms over SPI, sync search and Viterbi on hard (or soft) decisions | 512 bytes per 32 ms, x3 interpolation and OpenRTX's demodulator at 24 kHz |
| Module | `c6phyrx.c` (c6dmrrx with RX_RAW, soft values every 8th window) | `c6fmtap.c` (0x34 stepped every 5 s through 1c, 18, 3c, 9c); `c6fmtap_1c.c` holds 0x1C |

Both modules are receive only: no `tx_tone`, no key-up, registers and the AT1846S put back at the
end. A path B result also settles where the UV-380's ~300 Hz receive high pass comes from.

## Test signal (Pluto, 441.850, AG7EW MCW ident first and last)

`python3 -m modem.m17rx wav OUT.wav` makes it at 48 kHz, half scale (`pluto_bench.py send OUT.wav
--dev 4800` = M17's 2400 Hz outer; `--dev 3888` = DMR's 1944):

- 30 s multitone: 10, 20, 30, 50, 75, 100, 150, 200, 300, 500, 700 Hz, 1, 1.5, 2, 2.5, 3, 3.4,
  3.8 kHz at equal level, Schroeder phases, 0.2 s period, so any whole second gives the response
  on exact FFT bins;
- 30 s of spec M17 BERT (PRBS9, alpha 0.5, 750 frames). `--tones-s 0 --bert-s 10` gives BERT only.

## Bench jobs (jobs inbox, UV-380 receive only)

**R1 tap** (`m17rx-tap-*`): `uv380.cmd` listen 0, power 0, freq 441850; `uv380.rx tap` in the
background; wait for `tap start`; `pluto send job:m17rx.wav --dev 4800 --gain -50`; wait for
`end halves`.

**R2 phy** (`m17rx-phy-*`): the same with `uv380.rx phy`, then four Pluto sends of `bert10.wav`:
2400 Hz outer, 1944 Hz outer, and 2400 Hz at +-500 Hz carrier offset (how much the slicer
tolerates; `st` lines log the ADC's own DC offset, 0x4E / 0x4F).

Read them: `python3 -m modem.m17rx tap uv380.log --wav tap.wav` (per 0x34 setting: tone response
against 1 kHz, where it is within 3 dB, BERT frames and bit errors from the tap) and
`python3 -m modem.m17rx phy uv380.log` (window spacing, BERT syncs in the joined windows, the gaps
between them, 192 symbols = nothing lost, bit errors; the soft level histogram).

| Result | Then |
| --- | --- |
| A: syncs 192 symbols apart, BER low | M17 RX on the chip: an RX module (sync search, LSF, stream, Codec2 out the speaker), then the image's M17 mode on this path, then upstream |
| A: windows lose or double symbols | try 0x10 = 0x66 (slotted) and the 0x40 timing bits; the soft values may still carry the symbols |
| B: low corner under ~20 Hz with some 0x34 | software demodulator on the tap (OpenRTX's own, 8 kHz input, x3) |
| B: ~300 Hz high pass whatever 0x34 says | the tap is out for 4FSK (the sim); A or nothing without a mod |

## Results (2026-11-18, UV-380 receive only, Pluto at -50 dB gain on 441.850, RSSI -68 dBm)

**Path B works: the unmodified UV-380 receives M17.** The FM tap is DC coupled and flat once
0x34's band-pass and de-emphasis are off, and spec M17 BERT decodes from it.

R1, job `m17rx-tap-1118a` (01:27:49-01:29:49Z), the multitone then 750 BERT frames at 2400 Hz:

| 0x34 | Tone response against 1 kHz (10 Hz ... 3.8 kHz) | Within 3 dB | M17 BERT from the tap |
| --- | --- | --- | --- |
| **1C** (all off, 25 kHz RX bandwidth) | -1 dB at 10 Hz, flat to 3 kHz, -3 at 3.4 kHz, -8 at 3.8 kHz | **10-3400 Hz** | 247 frames, 75 of 48,659 bits wrong; one 5 s window 124 frames 0 wrong, the other 75 wrong (a sample glitch, below) |
| 18 (12.5 kHz RX bandwidth) | flat to 2.5 kHz, -6 at 3 kHz, -14 at 3.4 kHz | 10-2500 Hz | 141 frames, 21 bits wrong |
| 3C (de-emphasis on) | +15 dB at 10 Hz falling to -16 at 3.8 kHz | 10-1000 Hz | no frames |
| 9C (band-pass on) | -40 to -58 dB under 200 Hz | 300-3000 Hz | no frames |

- **No sub-audio high pass on our board.** RadioFoundry's "fixed ~300 Hz high pass" on the tap does
  not show with the AT1846S in its DMR set: 10 Hz reads -1 dB. The ~300 Hz cut we saw on the UV-380
  before (11-13, 11-14) is the band-pass (0x34 bit 7, which OpenRTX's FM set turns on) and the
  AT1846S FM set, not the C6000.
- **The tap is inverted**: +3 (above the carrier) reads negative. `m17rx` tries both polarities;
  an on-radio receiver negates the samples.
- **Level**: about 3 tap units per Hz of deviation (2400 Hz outer ~ 7400), no clipping at M17
  deviation; noise with no signal fills full scale.
- **Half glitches**: the first module found the complete half from sample 0 changes and slipped
  about once every 2 s (64 in 120 s); each slip costs a few frames' bits. 0x82 bit 1 came 31.25 times a second
  (3750 flags in 120 s) and coincides with the half switch, so `c6fmtap` now takes halves on that
  flag (`TAP_FLAG 1`) and picks the half whose last sample changed.

R2, job `m17rx-phy-1118a` (01:33Z): the physical layer test mode set from FM gave **no windows at
all** (`raw=0`, no slot interrupts). Path A would need the chip's DMR set-up first; with path B
working it is not needed.

R3, job `m17rx-tap1c-1118b` (02:09:31-02:12:08Z), `c6fmtap_1c` (0x34 held at 0x1C, halves on the
0x82 flag), `bert10.wav` (250 BERT frames) at five Pluto settings:

| Pluto gain | UV-380 RSSI | BERT frames (C receiver) | Bits wrong | Tap SNR, 0-2.4 kHz |
| --- | --- | --- | --- | --- |
| -50 dB | -68 dBm | 250 of 250 | 0 of 47,000 | high |
| -70 dB | -86 | 0 | | -0.4 dB (signal itself down to 0.72: FM threshold) |
| -80 dB | -91 | 0 | | -18 dB |
| -89 dB | -93 (the meter's floor) | 0 | | -28 dB |
| -50 dB, +1 kHz offset | -68 | 250 of 250 | 0 of 47,000 | high |

- **Flag-driven halves fixed the glitches**: 4688 halves in 150 s, 0 gaps, every one found by the
  last-sample rule (no guesses).
- **Carrier offset**: 1 kHz costs nothing (the receiver's DC follower takes it off).
- **The edge is between -50 and -70 dB** on the Pluto. At -70 the tap is at the FM threshold
  (SNR about 0 dB in the band), so no demodulator would get M17 out of it. For comparison the K6's
  2-level FSK at 2400 baud decodes to -93 dBm on its own meter (Pluto about -75 dB): M17's 4 levels
  at 4800 baud need more signal. R4 (below) finds the edge.

R4, job `m17rx-tap1c-1118c` (02:22:37-02:25:06Z), the same set-up; `traffic.wav` is two M17 SMS
and a 74-frame Codec2 voice stream (`tests/data/uv380/m17-voice.c2`) from AG7EW, decoded by the C
receiver from the tap:

| Send | UV-380 RSSI | Decoded | Bits wrong |
| --- | --- | --- | --- |
| traffic, -50 dB | -68 dBm | both SMS (CRC good, text exact), 3 LSFs src AG7EW, 74 of 74 stream frames, LICH good, Codec2 bytes exact | 0 |
| BERT, -55 dB | -73 | 250 of 250 | 0 of 47,000 |
| BERT, -60 dB | -77 | 250 of 250 | 0 of 47,000 |
| BERT, -65 dB | -81 | 250 of 250 | 35 of 47,000 (7e-4) |
| traffic, -60 dB, +1 kHz | -76 | both SMS, 74 of 74 stream frames, Codec2 exact | 0 |

- **The edge is sharp, between -65 and -70 dB** (RSSI -81 to -86): every frame at -65, none at -70,
  where the FM discriminator drops below threshold.
- 1 halves "alt" guess in 4687, 0 gaps.

## The receiver on the radio

`c/common/m17_rx.c` (MIT) is the C version of `modem/m17.py`'s receive side for 8 kHz tap audio:
DC follower, x3 interpolation and the RRC matched filter (alpha 0.5) in one polyphase filter,
sync correlation against all five syncwords at 24 kHz, least-squares gain from the sync, soft bits,
soft Viterbi, Golay LICH, CRCs. It locks to 40 ms frames (+-3 samples a frame for the far end's
clock) and only counts a frame whose Viterbi path is clean (hunting: at most 1 % of the soft weight
against it; locked: 6 %), so noise that matches a sync now and then makes nothing.

- On R1's tap capture: 390 BERT frames (388 with 0 bits wrong, 2 at the old half glitches); R3's:
  500 frames, 0 bits wrong; 20 minutes of full-scale noise: no frames.
- `tests/test_uv380_m17rx.py`: SMS, voice stream and BERT through a simulated tap, inverted.
- Floating point, no malloc, no writable statics, about 6.3 KB of state (the 24 kHz ring kept as
  16 bits).

`firmware/uv380-openrtx/mod/c6m17rx.c` is the RAM module: c6fmtap's set-up (0x34 = 0x1C, AT1846S
DMR set, flag-driven halves), the receiver in scratch (7.9 KB image + 6.6 KB state in the 16 KB
arena), and lines over USB for each frame: LSF callsigns, SMS text when its CRC checks, stream
frame numbers and LICH, BERT bit errors (PRBS9's self-synchronising check). `c6m17rx_tap.c` also
sends the tap audio so the host receiver can be run on what the radio had. Runner plans `m17` and
`m17tap` (`uv380.rx`).

**On the radio, job `m17rx-onradio-1118b` (02:54-02:57Z)**, `uv380.rx m17tap` (c6m17rx_tap):
the receiver ran on the UV-380 and printed what it decoded, with the tap lines beside it.

| Send | Decoded on the radio |
| --- | --- |
| traffic, -50 dB | `sms 5799 AG7EW: M17 RX ON UV380 DE AG7EW`, `sms 5959 AG7EW: NO MOD 73`, LSFs src AG7EW dst ALL, 74 of 74 stream frames with LICH good |
| BERT, -50 dB | 250 of 250 frames, 0 of 47,000 bits wrong |
| traffic, -60 dB, +1 kHz | both SMS again, 74 of 74 stream frames |

End line: `frames=417 lost=0 lsf=6 str=148 pkt=6 bert=250 eot=7 sms=4 bert_bits=47000 bert_err=0`,
0 half gaps in 150 s. `m17_rx_host` on the radio's own tap lines gives the same 417 frames.
Scratch: 8640 bytes after the image, 6640 used.

## Voice on the speaker (image API level 5)

The image's module API gains three calls (level 5, `ortx_mod.h`): `c2_start`, `c2_push`,
`c2_stop`, which hand Codec2 3200 frames to OpenRTX's own decoder thread and the MCU to speaker
path (the C6000's DAC), as OpenRTX's M17 mode plays a call. `c6m17rx` keeps a 32-frame jitter
buffer, starts the decoder once 6 frames (120 ms) are in, pushes as the decoder's 4-frame queue
takes them, and stops it 120 ms after a call's last frame (the last-frame flag, an EOT, or 400 ms
with no stream frame). Lines: `spk start q=6`, `spk stop frames=N gap=MS drop=N`.

`tests/c6m17rx_spk_host.c` runs the module's own frame and speaker code on the host against a
model of the decoder (one frame every 20 ms). On R4's and the on-radio run's tap captures: both
74-frame calls pushed whole (148 frames each run), the longest wait between stream frames 64 ms,
the decoder never dry mid-call.

Needs a flash: the image with level 5 (keyed Plus build), then `uv380.rx m17` with the Pluto
sending `traffic.wav`.
